# Implementation Plan A — Google Sheets backend

Replace the browser-only demo storage with a shared backend built on **Google Sheets + Google Apps Script**, so every SPG, Team Leader and Supervisor works on the same data.
The pages stay as they are (static HTML on GitHub Pages). Only the data layer changes.

> Status: plan. No code yet. Plan B (web backend with a real database) comes after this one is reviewed.

---

## 1. Goals and limits

| | |
|---|---|
| **Goal** | Real multi-user app for < 50 users, Rp 0 running cost, data the client can open as a spreadsheet |
| **Keeps** | All current pages, design, gamification, shifts, per-sale entry, photos, targets |
| **Changes** | `assets/js/data.js` talks to Apps Script instead of localStorage; real login; real dates |
| **Not in scope** | Native app, automatic WhatsApp sending (stays as a "wa.me" link), POS integration |

Known trade-offs of Apps Script (acceptable at this scale):
- Each request takes **~1–2 s**. The UI shows a loading state and saves sales optimistically.
- Max ~30 requests running at the same time per script; fine for < 50 users.
- Sheet limit is 10 million cells. Sales use ~180k cells per month at 50 SPGs → years of room; archive yearly.

## 2. Architecture

```
 SPG phone / Leader laptop                    Google (owner's account)
┌──────────────────────────┐   HTTPS POST   ┌───────────────────────────┐    ┌──────────────┐
│ GitHub Pages (static)    │ ─────────────▶ │ Apps Script web app       │ ─▶ │ Google Sheet │
│  pages + data.js         │ ◀───────────── │  Code.gs: auth, rules,    │    │  (private)   │
│  token in localStorage   │   JSON         │  read/write, cache, locks │ ─▶ │ Drive folder │
│  offline sales queue     │                └───────────────────────────┘    │  (photos)    │
└──────────────────────────┘                                                 └──────────────┘
```

- The **Sheet and Drive folder are private** to the owner account. Users never get Google access.
- The script is deployed as a web app: **Execute as: Me**, **Who has access: Anyone**. Every rule is enforced inside the script.
- Requests use `Content-Type: text/plain` with a JSON body, which avoids the browser's CORS preflight that Apps Script doesn't support.

## 3. Spreadsheet design (one tab per table)

Row 1 = headers. IDs are generated by the script. Dates `YYYY-MM-DD`, times `HH:MM`, timezone **Asia/Jakarta**.

| Tab | Columns | Notes |
|-----|---------|-------|
| **Users** | `id, username, name, role, area_id, team_id, store, phone, photo_id, password_hash, salt, token_version, active, created_at` | role = spg / leader / supervisor / admin |
| **Areas** | `id, name, supervisor_id` | |
| **Teams** | `id, name, area_id, leader_id` | |
| **Products** | `id, name, sku, price, photo_id, active, updated_at` | Admin maintains; may also be edited directly in the Sheet |
| **Targets** | `user_id, month, monthly, weekly, daily, set_by, set_at` | one row per SPG per month (`2026-10`) |
| **Shifts** | `id, user_id, date, start, end` | |
| **Sales** | `id, user_id, date, time, product_id, qty, price, subtotal, created_by, created_at, deleted` | **one row per sale**; deletes are soft (`deleted = TRUE`) |
| **Daily** | `user_id, date, total, tx_count, no_sales, unlocked` | one row per SPG per day, updated on every sale; dashboards read this, not Sales |
| **Settings** | `team_id, working_days, edit_days, reminder` | `working_days` like `1,2,3,4,5,6` |
| **Holidays** | `team_id, date, name, working` | |
| **LoginLog** | `time, username, success, ip_hint` | audit, optional |
| **Meta** | `key, value` | schema version, last archive, etc. |

**Photos** (profile + product) are not stored in cells (cells max 50k characters).
The app uploads the resized JPEG to the script, which saves it in a Drive folder, shares it "anyone with the link", and writes the file id to `photo_id`.
The app shows it via `https://drive.google.com/thumbnail?id=<id>&sz=w256`.

## 4. API (one endpoint, action-based)

`POST <script URL>` with body `{ action, token, ...params }` → `{ ok, data | error }`.

| Action | Who | What it does |
|--------|-----|--------------|
| `login` | everyone | username + password → token + user profile |
| `bootstrap` | all roles | everything the page needs for the user's scope: me, team(s), users, products, settings, holidays, targets (current + previous month), Daily rows (current + previous month), my/ team shifts today |
| `sales.list` | owner / leader / supervisor | Sales rows for `{ user_id?, team_id?, from, to }` (report details, CSV export) |
| `shift.start` / `shift.end` | SPG (own) | creates / closes today's shift (server time) |
| `sale.add` | SPG (own, during shift or inside edit window), leader/supervisor | appends a Sale, updates Daily; **idempotent** by client id |
| `sale.remove` | same as above | soft-deletes a Sale, updates Daily |
| `report.unlock` / `report.lock` | leader (team), supervisor | sets `Daily.unlocked` |
| `targets.save` | leader (team), supervisor (area) | upserts Targets rows |
| `settings.save` | leader (team), supervisor | Settings + Holidays for one team |
| `user.add` / `user.setActive` / `user.resetPassword` | leader (team SPGs), supervisor, admin | deactivation and reset bump `token_version` |
| `user.photo` | self, leader (team), admin | uploads photo to Drive |
| `product.save` / `product.photo` | admin | add / edit / activate products |
| `password.change` | self | old + new password |

Every action: verify token → load user → **check role and scope** → do the work → return fresh data for what changed.

## 5. Login and sessions

1. **Passwords** are stored as `SHA-256(salt + password)` hashed 1,000 times (Apps Script has no bcrypt). Unique random salt per user.
2. **Login** checks the hash and returns a **signed token**: `base64(payload).base64(HMAC-SHA256(payload, SECRET))`, payload = `{ uid, role, team, tv (token_version), exp (now + 30 days) }`. `SECRET` lives in Script Properties, never in the code or the Sheet.
3. The browser keeps the token in localStorage and sends it with every request.
4. The script verifies signature + expiry + `tv` matches the user's current `token_version` + user is active. Tokens are renewed quietly when they are older than 7 days.
5. **Logout** deletes the token in the browser. **Deactivate / reset password / "log out everywhere"** bumps `token_version`, so all old tokens stop working at once.
6. **Rate limit**: max 5 failed logins per username per 15 minutes (CacheService counter). Failed and successful logins go to LoginLog.
7. **First passwords**: a Leader or Admin creates the user with a temporary password; the user must change it on first login. Forgotten password = Leader resets it.

## 6. Data rules enforced by the script

- SPG writes only **their own** shifts and sales.
- `sale.add` for **today** requires an open shift; for a past day it must be inside the team's edit window (default 2 days) or the day must be unlocked.
- Prices: the sale stores the price actually charged; product price changes never alter past sales.
- Team Leader: only SPGs, targets, settings and reports of **their team**. Supervisor: all teams in **their area**. Admin: products and all users.
- Quantities ≥ 1, prices ≥ 0, dates not in the future, product must exist (inactive allowed only on old sales).

---

## 7. Speed, concurrency and offline

- **Locking**: every write runs inside `LockService.getScriptLock()` (wait ≤ 10 s) so two SPGs saving at once can't overwrite the same row.
- **Daily** rows are found through an index kept in CacheService (`user|date → row number`); rebuilt if missing.
- **Cache**: Products, Users, Teams, Settings are cached for 10 minutes in CacheService and cleared on every write to them. An `onEdit` trigger clears the cache when someone edits the Sheet by hand.
- **Client cache**: the last `bootstrap` is saved in localStorage, so pages open instantly and refresh in the background.
- **Optimistic sale entry**: a sale appears in the list immediately with a "sending" mark; it is confirmed when the script answers.
- **Offline queue**: if there is no signal (common inside malls), sales are kept in a local queue with their client id and time, and sent automatically when back online. The id makes resending safe (no duplicates).

## 8. Front-end changes

The pages already go through `Data.*`. To avoid rewriting them:

1. `assets/js/config.js` (new): `BACKEND_URL`. Empty = **demo mode** (today's local data), so GitHub Pages demo keeps working.
2. `data.js` gets a small API client (`call(action, params)`) and keeps the **same in-memory state shape**. On page load: `await Data.ready()` fills it from cache, then from `bootstrap`.
3. Read functions (`progress`, `leaderboard`, `teamSummary`, …) stay synchronous on that state; nothing changes in the pages that use them.
4. Write functions (`addSale`, `startShift`, `saveTargets`, …) become `async`: they update the local state, call the API, and roll back with a message if the server refuses.
5. Report details and CSV export call `sales.list` on demand.
6. **Real dates**: `TODAY` comes from the server time (Asia/Jakarta) instead of the fixed demo date.
7. Login page: real password check; "Ganti password" on first login; remove the demo account list in live mode.
8. Loading states and error toasts ("Tidak ada koneksi, penjualan disimpan dan akan dikirim otomatis").

## 10. Setup (done once by the owner of the Google account)

1. Create a Google Sheet "Laporan SPG – NIVEA" and a Drive folder "Laporan SPG – Foto".
2. In the Sheet: **Extensions → Apps Script**, paste the files from `server/`.
3. Project settings: timezone **Asia/Jakarta**. Script Properties: `SECRET` (random), `PHOTO_FOLDER_ID`.
4. Run `setupSheet()` once (creates tabs and headers), then `createAdmin("admin", "<temporary password>")`.
5. **Deploy → New deployment → Web app**, Execute as **Me**, access **Anyone**. Copy the URL.
6. Put the URL in `assets/js/config.js`, run `python3 tools/bump-version.py`, push.
7. Admin logs in, changes password, adds products (or pastes them into the Products tab), creates Supervisor/Leaders; Leaders create their SPGs.
8. Time triggers: nightly backup copy of the Sheet to Drive; yearly archive of old Sales rows.

## 11. Phases

| Phase | Work | Result |
|-------|------|--------|
| **1. Backend core** | Sheet schema, `setupSheet`, auth (hash, token, rate limit), router, `login` + `bootstrap` | Can log in against the Sheet and load data |
| **2. SPG flow** | shifts, `sale.add/remove`, Daily updates, locks, offline queue, optimistic UI | SPGs can work a full shift on real data |
| **3. Leader / Supervisor** | targets, settings, holidays, users, unlock, `sales.list`, CSV | Leaders manage their team for real |
| **4. Admin + photos** | products CRUD, Drive photo upload for users and products | Catalog and photos live |
| **5. Hardening** | backups, archive, cache invalidation on manual edits, LoginLog, error messages | Ready for a pilot |
| **6. Pilot** | 1 team for 1–2 weeks, then everyone | Go-live |

Each phase is a separate commit; demo mode keeps working throughout.

## 12. Testing

- **Local fake backend** (`tools/test-backend.js`) implementing the same API, so the existing Playwright tests run against "live mode" without Google.
- Script-side tests in Apps Script (`runTests()`): hashing, token sign/verify/expiry/revocation, permission matrix per role, edit-window rules, idempotent `sale.add`, Daily totals match Sales.
- Manual checklist on the real deployment: two phones saving sales at the same time, airplane mode during a shift, deactivate an SPG while logged in, password reset.

## 13. Decisions needed

1. **Whose Google account owns the Sheet?** (NIVEA's, the agency's, or yours.) The owner controls the data and the script.
2. **Offline sales queue**: needed from day one? (Recommended: yes, for mall basements.)
3. **Login**: username + password (as planned) or phone number + password?
4. **Hand edits in the Sheet**: allow Admin to edit Products/Users directly in the Sheet, or only through the app? (Recommended: Products yes, everything else app-only.)
5. **Photos in Drive** OK, or keep only generated avatars + product images in the repo?
